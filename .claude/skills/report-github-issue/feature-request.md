# Feature request

## Title

Name the requested capability, for example:
`Allow users to retry failed uploads`.

## Writing guidance

Keep the user problem distinct from the proposed feature. Describe impact as the
current burden on users, reach as the affected audience and its size, and cost of
inaction as the consequences of deferring the work. Avoid repeating the same
claim in all three sections.

Use supported numbers when available. Identify estimates as estimates and state
their basis; use `Unknown` when the size of the audience is unavailable. A known
user group is still useful even without a count. Describe existing workarounds
and their limitations under cost of inaction when known.

Make the desired outcome observable so an implementer can tell when the request
is satisfied. Describe the capability without prescribing an implementation
unless the user explicitly requires one.

## Body template

```markdown
### Summary

<1–3 sentences describing the requested feature>

### User problem

<What users are trying to accomplish and what prevents it>

### User impact

<How the problem affects users' work>

### Reach

<Which users are affected and approximately how many, when known>

### Cost of inaction

<Consequences of deferring the feature and any existing workarounds>

### Desired outcome

<Observable behavior that would satisfy the request>
```
